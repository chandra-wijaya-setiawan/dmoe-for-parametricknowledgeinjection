The DMoE architecture augments a frozen base model with modular LoRA expert modules attached to the final-layer feed-forward network. An uncertainty-aware BM25 router activates relevant experts only when the model lacks knowledge, preserving KV-cache reuse during autoregressive generation.

2. Experimental Journey — What Failed and Why

Attempt #1 — Naive Single Expert
❌ Training one LoRA on entire Wikipedia page (138K chars)

Each knowledge unit was a full Wikipedia article (30-165K chars). Trained 30 experts on Modal T4 GPU with LoRA r=16, α=32, 10 epochs on the entire page's content. Results: 0% improvement. The LoRA capacity (122K params) was insufficient to encode an entire Wikipedia page worth of knowledge.

Lesson: Each expert must encode ONE specific fact (~100 words), not a whole document. The paper uses 27,613 passage-level experts, not 30 page-level ones.

Attempt #2 — TU Formula Mismatch
❌ Using 1-max_prob instead of entropy for TU

The original TokenUncertainty.compute() used mean(1 - max_prob) which outputs values in [0, 1). The paper uses entropy TUt = -Σ pt(v) log pt(v) which outputs values in [0, ~12). We set τ=2.0 (paper default) but with the wrong formula, no expert was ever activated because TU never exceeded 0.92.

Fix: Changed TU to use full entropy. After fix, TU ranged 0.5–5.1, correctly triggering the router when the model was uncertain.

# Wrong (original)
def compute(logits):
    probs = torch.softmax(logits, dim=-1)
    max_probs, _ = probs.max(dim=-1)
    return (1.0 - max_probs).mean().item()

# Correct (paper §3.1)
def compute(logits):
    probs = torch.softmax(logits, dim=-1)
    log_probs = torch.log(torch.clamp(probs, min=1e-10))
    entropy = -(probs * log_probs).sum(dim=-1)
    return entropy.mean().item()
Attempt #3 — Expert Deltas Never Applied
❌ get_submodule("...weight") silently fails

The ExpertManager._apply_delta() used model.get_submodule(mod_key + ".weight") to locate the weight parameter. However, get_submodule() traverses nn.Module children — it cannot find .weight which is a Parameter, not a Module. The AttributeError was silently caught, so deltas were never applied to the model. All "DMoE" outputs were identical to the base model.

Fix: Use get_submodule(mod_key).weight — first get the Linear module, then access its .weight attribute.

# Broken
param = model.get_submodule(mod_key + ".weight")  # AttributeError: 'weight' is not an nn.Module

# Fixed
mod = model.get_submodule(mod_key)
weight = mod.weight  # Works: mod is the Linear, .weight is its parameter
Attempt #4 — Tiny Deltas (v1 training)
❌ 3 epochs, lr=2e-5 → delta std = 0.00009 (negligible)

Training with 3 epochs and lr=2e-5 produced LoRA deltas with std ≈ 0.00009, compared to the original weights' std ≈ 0.02. The delta was only 0.45% of the original weight magnitude — far too small to change the model's output. The base model confidently predicted "June 13, 2026" (wrong) and the delta couldn't override it.

Diagnosis: For Qwen2.5-3B (3B params), LoRA modifies only 69,120 params (0.002% of total). With 4 training examples and 3 epochs, the gradient signal is too weak to meaningfully shift the weights.

Attempt #5 — Multi-Expert Interference
❌ top-k=3 with 6 experts corrupts the model

When BM25 router selected 3 experts (top-k=3, paper default), all 3 experts modified the same 3 FFN weight matrices in layer 35. Their deltas accumulated and produced garbage output (repetitive "1999999999..." patterns). The model's FFN computation was overwhelmed by the combined delta of 3 unrelated experts.

Why the paper uses top-k=3: The paper has 27,613 experts from diverse Wikipedia domains. Each expert modifies a different knowledge subspace in the FFN. With only 6 experts all for the same domain (World Cup), each modifies the identical subspace — causing destructive interference.

# The problem: 3 experts all modify the SAME 3 layers
layer_35_ffn = {
    gate_proj: Δ₁ + Δ₂ + Δ₃  # Total delta = sum of 3 conflicting signals
    up_proj:   Δ₁ + Δ₂ + Δ₃  # Each expert pulls in different direction
    down_proj: Δ₁ + Δ₂ + Δ₃  # Result: corrupted FFN output
}

# Solution: top-k=1 for small expert pools
layer_35_ffn = { gate_proj: Δₓ }  # Single expert, clean signal

top-3: 0%
top-1: 47%

Each knowledge unit must be a single self-contained fact (~100 words). This is the single most critical design decision. The paper uses 27,613 such units from Wikipedia. Each unit includes:

5. Analysis for AI Engineers & Scientists

5.1 Why 200 Epochs?

The paper trains each expert for 1 epoch on a single A100 GPU (~10 seconds). Our setup has three key differences that required more epochs:

  • Smaller model, CPU training: Qwen2.5-3B on CPU converges slower than Llama-3.2-1B on A100
  • Prior knowledge override: The model already has (wrong) knowledge about WC2026 — "June 13" instead of "June 11". Overriding prior knowledge requires stronger deltas
  • Fewer training examples: 4 instances (1 rewrite + 3 QA) × 200 epochs = 800 gradient steps

5.2 Delta Magnitude Analysis

The threshold for effective knowledge injection was delta std ≈ 0.002 (≈10% of original weight std). Below this, the model's prior knowledge dominated.

5.3 Single Expert vs Multiple Experts

The paper's approach with 27,613 experts and top-k=3 relies on each expert encoding a different knowledge subspace in the FFN weights. When all our 6 experts encode World Cup knowledge (same subspace), applying 3 simultaneously causes destructive interference. This is a fundamental scaling property:

# With 27,613 diverse experts:
W_eff = W_base + Σᵢ Δθᵢ   where each Δθᵢ is near-orthogonal
→ KV-cache compatible, no interference ✓

# With 6 domain-specific experts:
W_eff = W_base + Σᵢ Δθᵢ   where all Δθᵢ modify the same subspace
→ Delta accumulation corrupts FFN computation ✗

Solution for small expert pools: top-k=1. The router selects the single most relevant expert, providing clean knowledge injection without interference.

5.4 KV-Cache Compatibility

By placing experts solely on the final-layer FFN (layer 35 for Qwen2.5-3B, which has 36 layers), the KV cache remains valid throughout generation. The hidden states feeding earlier attention layers are unchanged, meaning cached keys/values stay correct. This design is validated in the paper's Table 3 and Figure 4.

5.5 Training Data Quality Issues

Two experts produced incorrect outputs due to training data problems:

  • SA manager → "Thapelo Maseko": The training rewrite and QA pairs correctly state "Hugo Broos", but the model associated "Thapelo Maseko" (the goalscorer) with the manager role. With only 4 training examples, the LoRA lacked capacity to learn distinct entity-role mappings
  • Match scores → repetition: The expert trained on match results learned the format but overfit to the training patterns, producing repetitive outputs

6. Conclusion

✅ DMoE Parametric Knowledge Injection is Viable

We successfully demonstrated that decoupled LoRA experts with BM25 routing can inject post-cutoff knowledge into a frozen LLM. The key requirements are:

  1. Tiny, focused knowledge units — ~100 words per expert (paper's 27,613-expert approach)
  2. Sufficient training — 200 epochs to overcome prior knowledge (vs paper's 1 epoch for novel facts)
  3. Proper TU formula — Entropy (not 1-max_prob) for τ=2.0 threshold
  4. Correct weight application — get_submodule(key).weight not get_submodule(key + ".weight")
  5. Top-k=1 for small pools — Multiple same-domain experts interfere on the same FFN weights
